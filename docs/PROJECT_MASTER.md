1. نظرة عامة ورؤية المشروع
1.1 المشكلة
صناعة المحتوى المُعاد توظيفه (Clipping) من البودكاست الطويلة تنمو بسرعة، خاصة عبر حملات مثل Whop، لكن:

الأدوات الحالية (Opus Clip, Klap, Vidyo.ai) ضعيفة جداً في اللغة العربية (تفريغ، ترجمة، تشكيل).
أغلبها مدفوع بالكامل ولا يوجد خيار محلي/مجاني حقيقي.
لا توجد أداة تدمج بين المعالجة التقنية للفيديو وإدارة حملات الـ Clipping وحساب الأرباح في مكان واحد.
1.2 الحل
أداة شخصية تعمل محلياً على جهاز المستخدم (Local-First)، مبنية بالكامل على أدوات مفتوحة المصدر ومجانية، تُغطي كامل دورة حياة المقطع:

text

رابط/فيديو خام → تفريغ وترجمة → اكتشاف اللحظات القوية → قص وتصميم 
→ تجهيز للنشر → تتبع الحملة والأرباح → مكتبة بحث دائمة
1.3 المستخدم المستهدف (في البداية)
أنت شخصياً (Solo Clipper) تدير حملات Whop على بودكاست غربية، تحتاج سرعة وجودة عالية بالعربية بدون تكلفة اشتراكات شهرية.

1.4 الرؤية طويلة المدى
بعد إثبات الأداة لنفسها في الاستخدام الشخصي، تتحول تدريجياً إلى منتج SaaS يخدم صناع محتوى عرب آخرين.

2. المبادئ التوجيهية (غير قابلة للتفاوض)
هذه القواعد تحكم كل قرار في المشروع، ويجب على أي مطور جديد الالتزام بها:

#	المبدأ	التفسير
1	مجاني أولاً (Free-First)	أي ميزة جديدة يجب أن تُبنى بأدوات مفتوحة المصدر تعمل محلياً قبل التفكير بأي API مدفوع
2	محلي أولاً (Local-First)	النظام يجب أن يعمل بالكامل على جهاز المستخدم دون إنترنت إن أمكن (عدا الترجمة/الروابط)
3	لا اشتراكات إجبارية	إن استُخدم API مدفوع كخيار اختياري متقدم، يجب أن يبقى النظام يعمل بالكامل بدونه
4	الالتزام بالحقوق	لا معالجة لأي فيديو دون رخصة أو إذن استخدام واضح؛ تسجيل مصدر الترخيص لكل فيديو إلزامي
5	بنية معيارية (Modular)	كل ميزة = وحدة مستقلة (Module) يمكن تفعيلها/تعطيلها/استبدالها دون كسر النظام
6	قابلية التوسع	كل قرار تصميمي يُتخذ بعين الاعتبار لتحويل المشروع لاحقاً إلى SaaS متعدد المستخدمين
7	التوثيق أولاً	أي ميزة جديدة تُضاف يجب أن تُوثق في هذه الوثيقة (القسم 12) قبل الدمج (Merge)
8	لا استخدام احتيالي للمشاهدات	ممنوع أي أداة تزيّف مشاهدات أو تنتهك شروط منصات النشر أو حملات Whop

3.2 لغة البرمجة المقترحة
Python — لأن كل الأدوات المجانية القوية (Whisper, ffmpeg-python, pyannote, OpenCV, mediapipe) لها دعم أول-درجة فيه.

3.3 مبدأ التصميم: Pipeline قابل للتخصيص
كل فيديو يمر بخط أنابيب (Pipeline) من "محطات" (Stages) منفصلة، كل محطة:

تأخذ مدخلاً محدداً
تنتج مخرجاً محدداً (JSON أو ملف)
يمكن استبدالها بمحطة أخرى دون التأثير على البقية
هذا يسمح للمطورين بإضافة "محطة بديلة" (مثلاً: محرك تفريغ آخر) دون كسر النظام.

4. قائمة الأدوات المجانية الكاملة (Tech Stack)
هذا الجدول هو المرجع الرسمي لكل أداة مستخدمة. ممنوع إضافة أداة مدفوعة كافتراضي — فقط كخيار اختياري إضافي موثق بوضوح.

ترجمة بديلة أخف	Argos Translate	خفيف جداً، يعمل بدون GPU

4.4 تحليل المحتوى واكتشاف اللحظات القوية
الميزة	الأداة	ملاحظات

تحليل المشاعر لتحديد اللحظات المؤثرة	~~transformers (نموذج Sentiment منفصل)~~ → يؤديه الـLLM المحلي ضمن نفس الطلب	انحراف معتمد (2026-09-20): توفير ~500MB تحميل وخطوة معالجة كاملة، بنفس النتيجة العملية

محرك الاستدلال بلا نموذج (Fallback)	قواعد داخلية في core/analyze/heuristics.py	يضمن عمل الأداة كاملةً بلا Ollama إطلاقاً (المبدأ 1)
وضع hybrid (الافتراضي)	الاستدلال يرشّح ×2 ثم الـLLM يرتّب ويشرح	أدق من كلٍّ منهما منفرداً، وأرخص من إرسال الترانسكربت كاملاً
فصل المتحدثين (مضيف/ضيف)	pyannote.audio 3.1	~30MB، اختياري، يحتاج توكن HuggingFace مجاني
فحص السلامة وجودة الترجمة	قوائم كلمات في config/sensitive_words.yaml + فحوص بنيوية	يكشف الترجمة الفارغة/المكرّرة/غير العربية قبل النشر

4.13 أساس الاستخدام والالتزام بالحقوق (المبدأ 4)
الوضع	السلوك

القيمة تُسجَّل دائماً في metadata.json لكل مقطع مهما كان الوضع، وتبقى الفكرة الأخلاقية قائمة:
لا نشر بلا سند واضح. المفتاح personal_test وحده مُعلَّم publishable=False.
4.14 اللمسات النهائية والصيانة التشغيلية (مضاف 2026-09-21)
الميزة	الأداة	ملاحظات
تطبيع جهارة الصوت	فلتر loudnorm في ffmpeg (EBU R128)	مدمج في تمريرة reframe — صفر تبعيات وصفر تكلفة زمنية
ظهور/اختفاء ناعم	فلترا fade + afade	يُدمجان في آخر تمريرة ترميز موجودة، لا تمريرة جديدة
كنس الملفات المؤقتة	منطق Python فوق paths.tmp	أمر ar-clipper clean — يعالج المخلفات بعد المعالجات المنقطعة
استئناف الدفعات	فحص وجود المقطع الناتج	--resume يتخطّى المنتَج مسبقاً (14.6s ← 0.03s)
معاينة الخطة	--dry-run	يعرض المحطات والإعدادات دون لمس القرص
مخرج آلي	--json على أمر suggest	للأتمتة والسكربتات، بلا تلويث stdout

قاعدة معمارية معتمدة: لا تُضاف تمريرة ترميز جديدة لأي لمسة تجميلية. قياساً،
كلّفت تمريرة polish المستقلة +8.5s لمقطع 20s، فدُمج loudnorm داخل reframe (يعيد
ترميز الصوت أصلاً) والـfade داخل burn_subtitles إن وُجدت وإلا داخل reframe.
تحذير: يجب تمرير include_loudnorm=False عند بناء فلتر الصوت بعد reframe، لأن
التطبيع مرتين يُفقد الصوت ديناميكيته.

قيم التطبيع الافتراضية: ‎-16 LUFS جهارة، ‎-1.5 dBTP ذروة حقيقية، مدى 11 LU —
وهي القيم المناسبة لمنصات الفيديو القصير. مُتحقَّق بالقياس: ‎-21.8 ← ‎-16.1 LUFS.

6. المرحلة 1: النواة التشغيلية (MVP)
🎯 الهدف: معالجة فيديو واحد يدوياً من رابط إلى مقطع منشور جاهز، بأقل قدر من الميزات، لإثبات أن خط الأنابيب (Pipeline) يعمل.

⏱️ المدة التقديرية: أسبوعين إلى شهر (حسب الوقت المتاح)

6.1 الميزات المشمولة
 إدخال رابط فيديو (yt-dlp) وتحميله محلياً
 رفع فيديو محلي مباشرة
 استخراج الصوت من الفيديو (ffmpeg)
 تفريغ الكلام لنص مع توقيت (WhisperX / faster-whisper)
 دعم تعدد اللغات في التفريغ
 ترجمة النص للعربية (NLLB-200 محلياً)
 اختيار المستخدم يدوياً لبداية/نهاية المقطع (Timestamps)
 قص الفيديو (ffmpeg)
 تحويل المقطع لمقاس 9:16 (crop مركزي بسيط، بدون تتبع ذكي بعد)
 توليد ترجمة عربية مع توقيت (SRT)
 حرق الترجمة على الفيديو (ffmpeg + ASS بسيط)
 حذف الصمت الطويل تلقائياً (auto-editor)
 تصدير MP4 نهائي جاهز
6.2 خطوات التنفيذ بالترتيب
الخطوة 1: إعداد البيئة

text

- تثبيت Python 3.10+
- تثبيت ffmpeg على النظام
- إنشاء virtual environment
- تثبيت: yt-dlp, whisperx, faster-whisper, torch, auto-editor
الخطوة 2: وحدة الإدخال (Ingest Module)

دالة تأخذ رابط أو مسار ملف
تتحقق من صلاحية الرابط والترخيص (تنبيه يدوي للمستخدم بالموافقة)
تحمّل الفيديو بجودة مناسبة (720p كافية للمعالجة)
تخرّج: مسار الفيديو المحلي
الخطوة 3: وحدة التفريغ (Transcribe Module)

تمرير الفيديو لـ WhisperX
الحصول على: نص كامل + توقيت لكل كلمة + توقيت لكل جملة
حفظ النتيجة كملف JSON منظم في data/transcripts/
الخطوة 4: وحدة الترجمة (Translate Module)

تمرير كل جملة من الترانسكربت لـ NLLB-200
حفظ نص عربي مقابل لكل جملة مع نفس التوقيت الأصلي
الخطوة 5: واجهة اختيار يدوية (CLI بسيط)

عرض الترانسكربت مع التوقيت للمستخدم
المستخدم يكتب: وقت البداية، وقت النهاية للمقطع المطلوب
الخطوة 6: وحدة القص (Clip Module)

استخدام ffmpeg لقص المقطع المحدد من الفيديو الأصلي
الخطوة 7: وحدة حذف الصمت

تمرير المقطع المقصوص عبر auto-editor لحذف الفراغات الطويلة
الخطوة 8: وحدة إعادة التأطير البسيطة (Reframe - نسخة أولية)

تحويل الفيديو لمقاس 9:16 عبر crop مركزي ثابت (بدون تتبع ذكي بعد - هذا يأتي بالمرحلة 3)
الخطوة 9: وحدة الترجمة المرئية (Subtitles Module)

توليد ملف ASS بسيط (خط واضح، بدون تلوين متقدم بعد)
حرقه على الفيديو عبر ffmpeg
الخطوة 10: التصدير

حفظ الفيديو النهائي في data/clips/ بصيغة MP4
حفظ ملفات SRT/VTT بجانبه
6.3 معيار النجاح لهذه المرحلة
تستطيع تشغيل أمر واحد بالـ CLI، تعطيه رابط فيديو ووقت بداية/نهاية، ويخرج لك فيديو 9:16 مترجم للعربية وجاهز للنشر خلال دقائق.

7. المرحلة 2: الذكاء في الاختيار والمحتوى
🎯 الهدف: إزالة الحاجة للاختيار اليدوي للمقاطع، وإضافة توليد المحتوى النصي المرافق.

⏱️ المدة التقديرية: 3-4 أسابيع

7.1 الميزات المشمولة
 تحليل الفيديو واكتشاف أهم الأفكار واللحظات المؤثرة (LLM محلي عبر Ollama)
 اقتراح أكثر من مقطع قابل للانتشار تلقائياً
 اكتشاف القصص، الآراء القوية، الجمل المفاجئة، والأسئلة المهمة
 استخراج عدة أفكار من الفيديو الواحد
 إنشاء مقاطع Part 1 وPart 2 عند استمرار الفكرة (تحليل طول الفكرة زمنياً)
 فصل المتحدثين (pyannote-audio)
 إنشاء عناوين ووصف وهاشتاغات مناسبة (LLM محلي)
 اقتراح Hook قوي لأول ثواني الفيديو (LLM محلي)
 كشف الكلمات الحساسة أو الأخطاء في الترجمة (LLM + قوائم كلمات محظورة)
 تحسين الصوت وتقليل الضوضاء (noisereduce)
7.2 خطوات التنفيذ بالترتيب
الخطوة 1: إعداد Ollama محلياً

text

- تثبيت Ollama
- تحميل نموذج (Llama 3 8B أو Qwen2 7B - يعمل على جهاز عادي بدون GPU قوي)
الخطوة 2: وحدة فصل المتحدثين (Diarization Module)

تمرير الصوت عبر pyannote-audio
دمج النتيجة مع ترانسكربت WhisperX (مطابقة التوقيت)
تصنيف كل جملة باسم/رقم المتحدث (Speaker 1, Speaker 2...)
الخطوة 3: وحدة تحليل المحتوى (Analyze Module) — الأهم في هذه المرحلة

بناء Prompt مخصص يُرسل الترانسكربت كاملاً (أو مجزأ لقطع) للـ LLM المحلي
الطلب من النموذج: "حدد أفضل 5-10 لحظات قابلة للانتشار، مع توقيت البداية والنهاية، ونوع اللحظة (قصة/رأي قوي/سؤال/جملة مفاجئة)"
تحليل الأفكار الطويلة التي تحتاج تقسيم لـ Part 1/Part 2 بناءً على المدة الزمنية المقترحة
حفظ النتائج كـ JSON منظم (قائمة مقترحات)
الخطوة 4: وحدة توليد المحتوى (Content Generation Module)

لكل مقطع مقترح، إرسال نصه للـ LLM لتوليد:
عنوان جذاب بالعربية
وصف قصير
هاشتاغات مناسبة (عربية + إنجليزية)
اقتراح Hook (أول جملة/فكرة تُعرض في أول 3 ثواني)
الخطوة 5: وحدة الفحص (Safety Check Module)

قائمة كلمات حساسة (يُبنى ملف مخصص قابل للتوسعة)
تمرير الترجمة عبر الفحص + مراجعة LLM لأخطاء الترجمة المحتملة
الخطوة 6: تحسين الصوت

تمرير كل مقطع عبر noisereduce قبل التصدير النهائي
7.3 معيار النجاح لهذه المرحلة
تعطي النظام فيديو ساعة كاملة، ويرجع لك تلقائياً قائمة بـ 5-10 مقاطع مقترحة، كل واحد له عنوان وهاشتاغات وHook جاهز، دون أي تدخل يدوي في الاختيار.

8. المرحلة 3: الهوية البصرية والتصميم
🎯 الهدف: رفع المستوى البصري للمقاطع ليصبح احترافياً وقابلاً للتمييز كعلامة تجارية.

⏱️ المدة التقديرية: 3-4 أسابيع

8.1 الميزات المشمولة
 تتبع الوجه وتوسيط المتحدث تلقائياً (mediapipe + OpenCV)
 إضافة ترجمة عربية متزامنة مع الكلام (تحسين متقدم)
 تمييز الكلمات المهمة بألوان وحركات جذابة (ASS Karaoke-style)

 توفير قوالب تصميم متعددة للفيديوهات
 إنشاء صورة مصغرة للمقطع (Thumbnail)
 إنشاء عدة نسخ للمقطع بتصاميم أو بدايات مختلفة (A/B variants)
8.2 خطوات التنفيذ بالترتيب
الخطوة 1: وحدة كشف وتتبع الوجه (Reframe Module - نسخة متقدمة)

استخدام mediapipe لكشف موقع الوجه في كل فريم
بناء منطق تتبع سلس (Smoothing) لتجنب اهتزاز الكاميرا الافتراضية
التعامل مع حالة تعدد المتحدثين: التبديل الذكي بين الوجوه حسب من يتكلم (دمج مع بيانات Diarization من المرحلة 2)
إعادة تصدير الفيديو مقصوصاً على مقاس 9:16 مع الوجه دائماً في المنتصف
الخطوة 2: وحدة الترجمة المتقدمة (Advanced Subtitles)

استخدام pysubs2 لبناء ملفات ASS معقدة:

اختيار الكلمات "المهمة" عبر LLM (المرحلة 2) أو تحليل تكرار/أهمية الكلمة
الخطوة 3: نظام القوالب (Template System)

بناء ملفات Config (JSON/YAML) لكل قالب تصميم يحدد:
نوع الخط، حجمه، لونه
موقع الشعار

الألوان العامة للهوية
بناء 3-5 قوالب افتراضية جاهزة
الخطوة 4: وحدة الهوية الثابتة (Branding Module)

إضافة شعار ثابت (overlay عبر ffmpeg) في موقع محدد

الخطوة 5: وحدة الصورة المصغرة (Thumbnail Module)

استخراج أفضل فريم (اللحظة الأكثر تعبيراً، عبر تحليل حركة الوجه/الفم)
استخدام Pillow لإضافة نص جذاب فوق الصورة (مأخوذ من الـ Hook)
الخطوة 6: وحدة النسخ المتعددة (Multi-Variant Export)

توليد نفس المقطع بأكثر من قالب/Hook مختلف لاختبار الأداء (A/B Testing)

**انحراف معتمد 1 — OpenCV Haar بدل mediapipe لتتبّع الوجه:**
نسخة mediapipe الحالية (1.0.x) أزالت واجهة ``solutions`` وتتطلب تنزيل ملف نموذج
(.tflite) من Google عند أول تشغيل. هذا يكسر مبدأ "يعمل محلياً بلا شبكة".
مصنّف Haar يأتي **داخل حزمة opencv نفسها** فلا يحتاج تنزيلاً إطلاقاً. القياس على
فيديو اختباري (وجه ينتقل من 0.22 إلى 0.75 أفقياً): كشف 100% من العيّنات، ومسار
مطابق للحقيقة (انتشار 0.532 مقابل 0.53). النتيجة النهائية: **الوجه داخل الكادر في
8 من 8 لحظات مقابل 1 من 8 بالقص المركزي**، بكلفة +1.6s لمقطع 12s.
يبقى mediapipe مدعوماً كمحرك اختياري عبر ``reframe.face_engine: mediapipe``.

**انحراف معتمد 2 — ASS/libass بدل drawtext لنصوص الهوية:**
سببان: (أ) ``drawtext`` **غير مُجمَّع** في ffmpeg المرفق عبر imageio-ffmpeg
(تحقّقنا عملياً)، (ب) والأهم أنه لا يصل الحروف العربية — يعرضها منفصلة ومقلوبة.
أما libass فيمرّ عبر HarfBuzz ويعرض العربية صحيحة، وهو المحرك نفسه المستخدم
لحرق الترجمة أصلاً.

**تشكيل العربية في الصورة المصغّرة:** Pillow لا يصل الحروف ولا يطبّق BiDi،
و``arabic-reshaper``/``python-bidi`` تبعيتان إضافيتان. بُني جدول أشكال الحروف
(Unicode Presentation Forms) داخل ``core/design/thumbnail.py`` — حوالي 40 سطراً
تعالج الاتصال ولام-ألف وترتيب الأرقام واللاتينية. النتيجة مُتحقَّقة بصرياً.

**التزام قاعدة القسم 4.14:** كل عناصر الهوية (الشعار، العلامة المائية، شارة
الجزء) تُدمج في آخر تمريرة ترميز موجودة عبر ``compose_filter_graph`` — لا تمريرة
جديدة. الشعار يحتاج ``-filter_complex`` بمدخل ثانٍ، فوُسِّعت ``apply_filters``
بمعامل ``extra_inputs``.

التكلفة الزمنية الإجمالية للمرحلة 3 على مقطع 11s: **10.2s** شاملةً التتبّع
والهوية والصورة المصغّرة.

الخطوة 2: وحدة البحث (Search Module)

استخدام SQLite FTS5 للبحث النصي داخل كل الترانسكربتات المخزنة
مثال استخدام: "ابحث عن كل مرة تكلم فيها الضيف عن الاستثمار" عبر كل الفيديوهات السابقة
الخطوة 3: وحدة الطابور (Queue Module)

بناء نظام طابور بسيط (Python multiprocessing/threading بالبداية، أو RQ + Redis للتوسع)
إضافة عدة فيديوهات للمعالجة، تُنفَّذ تلقائياً واحدة تلو الأخرى بكامل الـ Pipeline (من المرحلة 1 إلى 4)
الخطوة 4: وحدة الدبلجة (Dubbing Module - اختيارية)

استخدام Coqui TTS أو Piper TTS لتحويل النص العربي المترجم إلى صوت
خيار للمستخدم: الإبقاء على الصوت الأصلي + ترجمة مكتوبة، أو استبداله بالكامل بالدبلجة
(متقدم اختياري): استخدام Coqui XTTS-v2 لاستنساخ نبرة صوت المتحدث الأصلي بالعربية
الخطوة 5: وحدة المعاينة (Preview Module)

عبر واجهة Streamlit/Gradio بسيطة: عرض الفيديو النهائي قبل الحفظ النهائي، مع إمكانية طلب إعادة معالجة جزء معين
الخطوة 6: وحدة التصدير متعدد المنصات (Multi-Platform Export)

بناء إعدادات تصدير مختلفة لكل منصة (مثال: X له حد مدة مختلف عن TikTok)
تصدير تلقائي بكل الصيغ المطلوبة دفعة واحدة
10.3 معيار النجاح لهذه المرحلة
تقدر تضيف 10 فيديوهات للطابور قبل النوم، وتصحى تلاقي عشرات المقاطع الجاهزة منظمة بمكتبة قابلة للبحث.

11. المرحلة 6: التوسع إلى SaaS
🎯 الهدف: تحويل الأداة الشخصية إلى منتج متعدد المستخدمين (فقط بعد إثبات نجاحها الشخصي).

⏱️ المدة التقديرية: تُحدَّد لاحقاً حسب الحاجة

11.1 المتطلبات الأساسية للتحول
 فصل منطق المعالجة (Core Engine) عن الواجهة بشكل كامل عبر REST API (FastAPI)
 بناء نظام مستخدمين (Authentication) وقواعد بيانات متعددة المستأجرين (Multi-tenant)
 بناء واجهة ويب حديثة (Next.js/React)
 التفكير في استضافة تعالج GPU (هنا فقط قد تحتاج تكلفة، لكنها تُدرس لاحقاً وليست جزءاً من النطاق الحالي)
 نظام اشتراكات/دفع (Stripe أو بديل محلي)
⚠️ هذه المرحلة خارج نطاق التنفيذ الحالي بالكامل — يُكتفى هنا بالتخطيط المعماري فقط لضمان أن القرارات التقنية بالمراحل السابقة (خصوصاً البنية المعيارية) لا تعيق هذا التحول مستقبلاً.

12. دليل المساهمة للمطورين (Contribution Guide)
12.1 مبدأ المشاركة
هذا المشروع مفتوح لإضافة أي ميزة أو تعديل بشرط الالتزام الصارم بالمبادئ في القسم 2، وتحديداً:

الأداة المستخدمة يجب أن تكون مجانية ومفتوحة المصدر وتعمل محلياً
أي استثناء (أداة مدفوعة اختيارية) يجب أن يكون:
غير افتراضي (Opt-in فقط)
موثقاً بوضوح في هذه الوثيقة مع تحذير صريح
النظام يجب أن يعمل بكامل وظائفه الأساسية بدونه
12.2 خطوات إضافة ميزة جديدة
افتح Issue يشرح: الميزة المقترحة، لماذا تفيد المشروع، الأداة المجانية التي ستُستخدم
تحقق من التكرار — تأكد أن الميزة غير موجودة أو مخطط لها مسبقاً في هذه الوثيقة
حدد الموقع الصحيح في هيكلة المجلدات (القسم 5) — كل ميزة يجب أن تكون Module مستقل
اكتب اختباراً بسيطاً (Test) يثبت أن الميزة تعمل بمعزل عن باقي النظام
حدّث هذه الوثيقة — أضف الميزة في الجدول المناسب (القسم 4) وفي خطوات المرحلة المرتبطة بها
قدّم Pull Request مع وصف واضح للتغيير
12.3 معايير رفض المساهمة
أي ميزة تتطلب اشتراك مدفوع إجباري
أي ميزة تنتهك حقوق النشر أو شروط استخدام المنصات
أي ميزة تساهم في تزييف المشاهدات أو التفاعل
كود غير موثق أو بدون اختبار بسيط
كسر البنية المعيارية (Module يعتمد بشكل مباشر وصلب على Module آخر بدل واجهة واضحة بينهما)
12.4 اقتراح تحسينات (وليس فقط ميزات جديدة)
مرحّب بأي اقتراح تحسين لأداة موجودة، مثل:

استبدال نموذج بنموذج مجاني أفضل/أسرع
تحسين جودة الترجمة عبر Prompt أفضل
تسريع المعالجة (مثال: استخدام faster-whisper بدل whisper الأصلي)

14. المخاطر التقنية والبدائل المجانية
الخطر	الحل البديل المجاني
الجهاز الشخصي ضعيف لتشغيل Whisper/LLM محلياً	استخدام نماذج أصغر (Whisper base/small، Llama 3 8B بدل 70B)، أو faster-whisper المحسّن
جودة الترجمة الآلية (NLLB) ضعيفة أحياناً	تمرير ناتج NLLB عبر LLM محلي (Ollama) لإعادة الصياغة وتحسين الأسلوب
تتبع الوجه غير دقيق مع حركة سريعة	استخدام Smoothing algorithms (متوسط متحرك) على إحداثيات mediapipe لتقليل الاهتزاز
فصل المتحدثين (pyannote) يحتاج توكن HuggingFace	التسجيل مجاني بالكامل، فقط قبول شروط الاستخدام على الموقع
سحب المشاهدات التلقائي من TikTok/Instagram صعب/مكلف	البقاء على الإدخال اليدوي، أو استخدام YouTube Data API الرسمي المجاني ضمن حدوده فقط
الدبلجة الصوتية (TTS) قد تكون بطيئة على CPU	استخدام Piper TTS (أخف بكثير من Coqui) كخيار افتراضي للأجهزة الضعيفة
معالجة عدة فيديوهات تستهلك مساحة تخزين كبيرة	حذف تلقائي للملفات الوسيطة (temp files) بعد انتهاء كل مرحلة من الـ Pipeline
